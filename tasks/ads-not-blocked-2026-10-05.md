# 「広告が全く消えない」調査（2026-10-05）

## 発端
- 利用者の FB「広告ブロックで全く広告が消えない」（問い合わせ。本文は Slack 側）
- kureho 本人の端末（KPhone・iPhone 17 Pro）でも「全然ブロックできていない」
- 10/3 の kureho 報告「一回外して再度 ON にしたら広告が出るようになった」→ 4.4.1 で「アプリ終了でコンパイルが止まる」として修正・10/4 01:04 JST 配信。**それでも直っていない**

## 確かめたこと（すべて実測）
| 確認 | 結果 |
|---|---|
| 配信中ルール 5 本（merged / second-ads-sec / second-ads / security / popunder）を Mac の WebKit でコンパイル | 全部 OK（merged 5.2 秒） |
| merged-rules で代表的な広告網のスクリプトが止まるか（Mac） | googlesyndication・doubleclick・i-mobile・taboola・outbrain 等を止める。対照の jQuery は通る＝**ルールの中身は正常** |
| 4.4.1 をシミュレータ（iOS 26.3）に新規インストール → 拡張 2 本 ON → Safari で試験ページ | 5 広告網すべて BLOCKED |
| 同じ機体でトグル OFF→ON → 60 秒待って試験ページ | すべて BLOCKED（シミュレータでは再現しない） |
| Safari の読み込み係 `com.apple.SafariServices.ContentBlockerLoader` の最大メモリ（シミュレータ・RSS） | **変更前ルール（9/1 版 merged）683MB → 現行（9/27 以降）824MB＝+21%** |
| Mac でのコンパイルの最大メモリ（footprint） | 9/1 版 358MB / 9/27 直前 358MB → **現行 487MB（+36%）**。2 本目 second-ads-sec 214MB |
| CDN merged の推移 | 9/1: 150,000 件・22.5MB → **9/27（A-88 ①）: 148,800 件・27–28MB**。2 本目は 40 件 → 約 4.8 万件・12.6MB |

## 仮説（当初・→ 下の「原因確定」で一部訂正: 落ちるのは読み込み係ではなく拡張）
A-88 ①（4.4.0・9/27 生成・9/28 配信）で基本保護を「重要 → 通信の遮断 → 要素隠し」で詰め直し、2 本目にも広告の残りを載せた結果、
**実機の ContentBlockerLoader がメモリ上限に当たって落ち、Safari への読み込みが失敗している**。シミュレータには上限が無いので通る。

- 失敗しても Safari は前回コンパイル済みのルールを持ち続ける → 4.4.0 に上げた直後は旧ルールが残って気づかない
- トグル OFF で小さいルール（詐欺サイトのみ・3 万件）は読み込めて置き換わる → ON の大きいルールは失敗 → 広告ブロックなしが残る＝**10/3 の kureho 報告と一致**
- 新規インストールの人は一度も読み込めない → 「全く消えない」＝**今回の FB と一致**
- 4.4.1 のやり直し（3 回まで）は、毎回同じ理由で失敗するので効かない

外部の同型報告:
- Apple 開発者フォーラム「件数は上限内なのに実機で読み込みに失敗」（`NSCocoaErrorDomain Code=4097 connection to service named com.apple.SafariServices.ContentBlockerLoader`・FB16477099・未解決）https://developer.apple.com/forums/thread/774008
- AdGuard v4.5.1（iOS 17）: 15 万件の上限より手前でクラッシュ → JSON のサイズを絞って回避 https://adguard.com/en/blog/adguard-v4-5-1-for-ios.html

## KPhone のクラッシュ記録（10/5 14:30 取得・100 件）＝メモリ上限説を支持しない
- JetsamEvent は 9/10〜10/5 に 7 件。**Safari の読み込み係（ContentBlockerLoader）・広告消しの拡張が落とされた記録は 0 件**
  （上限超過で落とされたのは momentsd 9/25・managedappdistributiond 10/5 のみ＝上限で落ちれば記録は残る）
- ほかの記録にもコンテンツブロッカー関連の痕跡なし（Safari の軽い不具合記録 10 件は 9/9 から出ており A-88 より前）
- → 「実機でメモリ上限に当たって落ちる」は**可能性が下がった**。失敗の仕方を直接見るには、読み込みの最中の端末ログが要る

## ★原因確定（10/5 14:35 KPhone の端末ログ・kureho の操作でトグル オフ→オン）
| 時刻（録画開始から） | 起きたこと |
|---|---|
| 00:24.7 | トグル オフ → 基本保護が「詐欺サイト対策だけ」3.5MB を返す → Safari が読み込み **成功** |
| 00:31.36 | トグル オン → 基本保護の拡張が広告ルール（27.6MB）を Safari に渡し始める |
| 00:31.40 | **`Process ContentBlockerExtension [44237] killed by jetsam reason per-process-limit`**＝基本保護の拡張が**メモリ上限で強制終了** |
| 00:31.40 | Safari 側: `Failed to load content blocker ... because the load was interrupted`（NSExtensionErrorDomain -2）→ **広告ブロックが入らないまま** |
| 00:40.2 | 2 本目（報告反映）の 12.6MB は読み込み **成功**（2.3 秒） |

- 落ちているのは Safari の読み込み係ではなく、**アプリ側の拡張（基本保護）そのもの**。拡張はルールのファイルを丸ごとメモリに載せて Safari へ渡す（`Extension/ContentBlockerRequestHandler.swift` の `NSItemProvider(contentsOf:)`）ので、**ファイルの大きさ（バイト数）がそのまま拡張のメモリ**になる
- A-88 ①（9/27）で基本保護のファイルが **20.6MB → 27.6MB**。件数は 13 万→14.9 万だが、効いたのはバイト数: 例外（止めないで）が **1,874 件 0.2MB → 8,985 件 7.55MB**（2 本の両方に全部入れる設計のため）
- 実機で読めた実績: 20.6MB（9/27 以前の基本保護・数か月）・12.6MB（今日の 2 本目）。読めない: 27.6MB（今日）
- 同梱（アプリ内）の基本保護も 4.4.0 以降 27.0MB＝通信できない初回もアウト
- クラッシュ記録に残らなかった理由: 端末はこの種の記録を **1 日 1 件まで**しか保存しない（ログに `Report of type '298' not saved because the limit of 1 logs has been reached`）。10/5 の枠は 12:04 の別件で使われていた
- シミュレータで再現しないのは、拡張のメモリ上限がシミュレータに無いため
- 端末ログ（録画・書き出し・クラッシュ記録）は 10/5 17:02 にこの Mac の作業フォルダから削除済み・外部送信なし（kureho との約束どおり。実機確認の録画も同じ扱い）

## 直し方（10/5 確定・この順で一気通貫）
**原則: 拡張が Safari に渡す 1 本のファイルを、実機で読めた実績の大きさより下に収める**（件数の上限 15 万とは別に、バイトの上限を持つ）。
上限 = 配信ファイル 1 本 **19.5MB**（実績 20.6MB の下・読めなかった 27.6MB）。アプリが実行時に足す分（報告ルール・ポップアップ対策・一時オフ）用に 0.5MB 空け、拡張が渡す最終の大きさは 20MB 以下。

1. **配信（CDN）— アプリ更新なしで全員に届く**
   - `scripts/build_split_rules.py`: 件数に加えてバイトの枠で振り分ける（基本保護・2 本目とも 19.5MB。2 本目はセキュリティ用に 4MB を固定で空ける）。入り切らないものは優先順の最後（サイト別の要素隠し）から捨てる。週次のセキュリティ入れ替えもバイトを確認
   - `scripts/convert.sh`: 新しいファイルが今のファイルの半分未満の件数なら止める（アプリは前回の半分未満を壊れたファイルとして捨てる＝配っても入らない）
   - 手元で月次と同じ変換を回して docs/cdn を作り直す → Mac の WebKit でコンパイル・広告網の遮断を確認 → push
   - **KPhone で実機確認**: 端末ログで「基本保護の読み込み成功（Compiling ... succeeded）」を見る
2. **アプリ 4.4.2 — 同じ事故を二度と起こさない守り**
   - 同梱の基本保護を 1. の出力で作り直す（今は 27.0MB＝通信できない初回もアウト）＋同梱ファイルの大きさをテストで縛る
   - 配信ファイルの受け取り（RuleUpdater）: 上限を超えるファイルは受け取らない（今のファイルを使い続ける）
   - 拡張: 渡すファイルが上限を超えていたら同梱に切り替える（最後の砦）
   - 2 本目の組み立て（報告ルールを足す）: 上限を超えたら組み立て直さない
3. **提出前の確認**: 実機での読み込み成否を端末ログで確かめる手順を入れる（シミュレータには拡張のメモリ上限が無く、原理的に見つけられない）
