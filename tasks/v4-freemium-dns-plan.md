## 確定した設計（kureho 最終承認待ち）

- **本体無料**: Safari CB 3拡張（基本保護=凍結修理して「生きたフィルタ」に / 報告反映 / 遷移保護のうち基本保護のみ無料）
- **Pro 買い切り ¥800**（¥980 から引き下げ・非消耗型 IAP）: DNS 型アプリ内広告ブロック（ローカル VPN・端末内処理）+ 報告反映 + 遷移保護
- **既存購入者（¥500/¥700 世代）**: 自動で恒久 Pro（grandfather）
- 差別化3点: ①端末内処理（280blocker の DNS は自社サーバー送信方式 → プライバシー差別化）②「ずっと買い切り・サブスク化しません」宣言（280blocker サブスク反発層の受け皿）③報告で進化する日本語アプリ特化フィルタ
- 訴求規律: 「他アプリの広告も**抑える**」（「消える」断定 NG）+ 限界明記（YouTube/X/Instagram/一部ゲームは不可）。metadata 価格表記 NG（2.3.7）・description に規約/ポリシーリンク必須（QReate reject 前例）

## 価格 ¥800 の根拠（2026-07-14 調査）
- AdGuard 無料版に DNS 保護は無い（Premium 限定・公式 KB）= Pro の対価は成立
- ただし**280blocker が ¥800 買い切りに DNS 標準搭載（2025-04〜）**= 国内価格アンカー。¥980 はこれを超えて見えるため非推奨
- 海外勢: AdGuard Pro ¥1,500 / AdLock ¥1,980 / 1Blocker LT ¥6,000 → ¥800 は空席の下限
- 無料経路（公共 DNS+プロファイル）は日本語圏に普及済みだが摩擦大 = ワンタップの対価は成立

## 技術方式（プランB・検証済み）
- **NEPacketTunnelProvider（ローカル VPN・DNS のみ claim する split tunnel）**。通信は外部サーバー非経由・ブロック判定は端末内
- リスト配信: 既存 GitHub Pages CDN（無料・稼働中）/ 報告パイプライン: 既存 CF Workers Free 枠（DNS クエリはさばかないので無料のまま）→ **運用費ゼロ**
- entitlement: packet-tunnel-provider（capability のみ・申請不要）。5.4 組織要件 → KUREHO 組織登録済み（2026-04-13）でクリア
- 実装参考: dnscrypt-proxy(ISC・流用可) / AdGuard iOS は GPL-3.0 で**流用不可** / DNS パーサ最小実装（query/response + NXDOMAIN/0.0.0.0 応答 + 上流転送）
- 制約 UI 明記: 他 VPN と排他 / VPN 表示（「外部サーバー非経由のローカル処理」説明画面）/ Network Extension のメモリ上限（正確な現行値は未確認）
- 審査確度: ローカル VPN 型は中（50-70%）・往復1-2回想定・却下でも既存 Safari CB 版は無傷

## grandfather 実装チェックリスト（調査の罠込み・実装時必読）
- [ ] 閾値 =「転換ビルドの CFBundleVersion 未満」**Int 変換後の数値比較**（Apple 公式サンプルは文字列比較でバグる）
- [ ] 転換ビルドのビルド番号を大きくジャンプ（例: 10000）— 履歴の非単調リスクの一掃
- [ ] `AppTransaction.environment == .production` の時のみ grandfather 有効（sandbox/審査/TestFlight は "1.0" を返す → **無効化しないと審査員が grandfather されて購入導線が消え 2.1 reject**・2026-01 実例 forums 814236）
- [ ] DEBUG 限定 Pro オーバーライド（シミュレータは AppTransaction 不可）
- [ ] 一度 grandfather 成功したら**恒久ローカル永続化**（UserDefaults+Keychain・以後の読み取りが flaky でも剥奪しない）
- [ ] 起動時は `AppTransaction.shared` のみ・失敗時は黙って無料扱い（過少付与に倒す）。`refresh()` はシステム認証プロンプトが出るため**ユーザー明示操作（復元ボタン）起点のみ**
- [ ] What's New/設定に「以前ご購入いただいた方はこちら（復元）」導線（thatvirtualboy 実績パターン）
- [ ] `AppTransaction.shared` のハング報告あり → タイムアウト設計
- [ ] 古い購入で originalAppVersion 欠落の報告 → **originalPurchaseDate を補助判定**（閾値日以前なら付与）の二段構え
- [ ] **Pro 状態でも購入/復元/Pro 状態表示 UI に到達可能**にする + 商品ロード失敗の明示 UI（814236 の reject 2 対策）
- [ ] Pro 判定 = grandfather OR `Transaction.currentEntitlements` の二本立て
- [ ] **フェーズ0 必須実測**: 本番購入済み実機で「削除→再インストール→AppTransaction」の挙動確認（originalAppVersion が購入時のまま保持されるかは公式明示なし・証言矛盾 = 本計画最大の残存不確実性。TestFlight では検証不能）

## 転換リリース手順（窓問題の回避・調査の手順書）
1. 事前: 過去全リリースの CFBundleVersion 履歴一覧化 / 実機実測（上記）/ IAP「Pro」作成（**初回 IAP は新バージョンと同時提出が公式必須**）/ description に規約・ポリシーリンク
2. **手動リリース（Pending Developer Release）で提出**・Phased Release オフ・**評価リセットは絶対に選ばない**
3. 審査ノート（英語・調査の実績文例ベース）: 転換の説明 + 「価格はリリース前に無料へ変更する」+ 「審査環境では legacy 判定を意図的に無効化してあるので購入フローがフルに見える」+ アカウント不要
4. 承認後: **即時価格変更で無料化 → 実機ストアページで ¥0 確認 → 分単位で即「このバージョンをリリース」**（順序の根拠: 逆だと窓中の ¥500 購入者が grandfather から漏れる=有害方向。この順なら窓は「無料 DL 者への Pro 過剰付与」=無害方向。深夜帯実行）
5. リリース後: 新規/旧購入者の両判定を実機確認 / **LP・スクショ等の「¥500 買い切り」表記を全更新（2.3.1 false price = 削除根拠になり得る）** / 数日レビュー監視（「Pro が消えた」→復元案内）
- 可逆性: 有料に戻すのは正規機能で可能。ただし無料期間の入手者の権利は恒久

## 収益見立て（正直な期待値・調査ベース）
- 月100〜300 DL（無料化+無人キーワード）× 転換2〜4%（DNS の強い機能ゲートで自社実測2%から上振れ余地）× ¥800 = **月¥1,600〜9,600**。「アプリ内広告」キーワードが刺されば上振れ・評価/順位の複利が毎月積む
- 転換で収益が増えた数字付き一次証言はゼロ（減収証言2件）— 楽観しない。撤退判定: 転換後3ヶ月で月販0-1本なら追加投資停止（塩漬けへ）
