## 決めたこと

- **並べ方**: 日本向け（`.jp` で終わる・日本の会社名などの語）→ URLhaus（上限 1 万）→ 海外ブランド（amazon・apple など）→ その他。段の中は名前を sha256 にした順（名前順の偏りを無くし、毎週同じ物は同じ位置に来る）。元の一覧に無いホストは 1 件も足さない
- **語**: `scripts/data/jp-priority-tokens.txt`（日本向けの語・語の完全一致・海外ブランドの 3 種）。件数は調査 §4-4 と完全に一致した
- **入れない物**: 人気サイト（Tranco 上位 100 万）その物とその上／人気サイト（上位 10 万）の下（共有ホストの利用者の物を除く）／重要ドメイン約 50 その物・その上・その下（Safari では間に共有ホストがある利用者の物を除く）／共有ホストその物／日本の公的機関・団体の `.jp`
- **人気サイトの線を 10 万位にした理由**: 10 万位までで、確認で名前が挙がったサービスの住所は全部外れる。100 万位まで広げると、今の 3 万件から 1,073 件が外れ、うち 47 件は日本向けの段（`onamaeweb.jp`・`hustle.ne.jp` などの日本の場の利用者を含む）。10 万〜100 万位の帯は見本を見きっておらず、共有ホストの一覧に無い場の利用者（＝本物の詐欺の住所）が多いので、広げなかった。代わりに計測の表に「100 万位まで」の行を出して見えるようにした
- **共有ホスト（その物は入れない・下の個別のホストは入れる）**: 手で選んだ `scripts/data/shared-hosting-parents.txt` に加え、公開のサフィックス一覧（PSL）の「事業者が自分で登録した共有ホスト」の節（3,458 行）を `scripts/data/psl-private-suffixes.txt` として使う。計画では PSL は確かめにだけ使う予定だったが、元の一覧に `s3.us-east-2.amazonaws.com`・`fra1.digitaloceanspaces.com` などの共有の入口その物が入っていて、手で選んだ一覧では拾えなかった。元の一覧には `bit.ly`・`dweb.link`・`cloudflare-ipfs.com`・`firebasestorage.googleapis.com` その物も入っていた（今の選び方では 3 万件の外だった）
- **S3 のバケット**: Safari 用では、重要ドメイン（amazonaws.com）の下でも、間に共有ホスト（`s3.amazonaws.com` など）がある個別のバケットは入れる（62 件）。止めても amazonaws.com そのものは止まらない（設計「共有ホストの親その物は入れない・その下の個別のサブドメインは入れてよい」）。ただし `us-east-1.amazonaws.com` のように事業者自身のサービスが並ぶ入口は境目にしない。DNS 用は計画どおり外す
- **語を見る範囲**: 共有ホストの下・人気サイトの下では、それより左（利用者が決めた部分）だけで語を見る（`xyz.s3.amazonaws.com` の「amazonaws」は Amazon の偽装ではない）
- **新しさは使わない**: Phishing.Database に新着だけのファイル（NEW-today）はあるが、10/2 から止まっている。ACTIVE は「今も生きている物」で既に絞られている。新着の履歴を持つには配信側に状態が要る
- **下限**: Tranco 90 万・Phishing.Database 10 万（どちらも違う名前の数）を割ったら止める。できた件数が枠の半分（15,000）未満でも止める。止めた時は CDN は前の週のまま
- **URLhaus**: 取れないので `--urlhaus` を省略できるようにした（今のワークフローの書き方のままでも読める）。計測は URLhaus 無し
- **確かめられなかったので入れていない共有ホストの候補**: `xsph.ru`・`tmweb.ru`・`tw1.ru`・`temp.swtest.ru`・`webcindario.com`・`co.vu`、日本の場の `blogspot.jp`・`mixh.jp`・`xsrv.jp`・`xdomain.jp`、IBM の保存場所の地域の入口（どれも公式の説明で確かめていない）。入れないと止める範囲が狭まる側（その利用者の詐欺の住所を取りこぼすが、関係ないサイトは止めない）

## 言えないこと

- 人気サイト（10 万〜100 万位）の中のサービスの住所が、まだ残っているかもしれない（「100 万位まで」の 1,073 件。見本は見たが全部は見ていない）
- 元の一覧の「ACTIVE」は名前が引ける物という意味と理解している（確かめていない）。10/2 から止まっているので、直ったサイトも一覧から消えない
- 実機での読み込みの時間は測っていない（Mac の CPU 時間で今とほぼ同じ）

```diff
-      - name: Fetch URLhaus host file (public, no auth required)
-        run: |
-          curl -fsSL "https://urlhaus.abuse.ch/downloads/hostfile/" \
-            -o /tmp/urlhaus-hosts.txt
-          echo "URLhaus lines: $(wc -l < /tmp/urlhaus-hosts.txt)"
-
       - name: Fetch Phishing.Database active domains (public, no auth required)
 …
           python3 scripts/build_security_rules.py \
-            --urlhaus /tmp/urlhaus-hosts.txt \
             --phishing-db /tmp/phishing-db-active.txt \
```

1. ワークフローの変更をブランチに足す → main へ merge → push
2. `gh workflow run build-security-rules.yml` → 終わるまで見る。期待: 成功・`chore(security): weekly auto-update` のコミット
3. 配信中の物（`security-rules.json`・`second-ads-sec.json`・`version-security.json`）を取り直し、計測の表を配信中の物で回して同じ線を満たすこと（読めない規則 0・トップが止まる 0・人気サイトの中の住所〈10 万位まで〉0・公的機関・団体の .jp 0・数字始まりの偏りなし）。`version-security.json` の sha が配信物と一致すること
4. 失敗した時: ワークフローは止まれば CDN を前の版のまま残す。壊れた物が出た時は revert のコミットを push してワークフローを手で回し戻す

Phishing.Database が止まっている間は、毎週同じ元データから同じ一覧ができる（Tranco の入れ替わりで数件動く程度）。

## G1（看板）の前に決める必要があること

元の一覧が 10/2 から止まっていて、日本向けの詐欺サイトをほとんど持っていない（上の事実 4・5）。この状態で「詐欺サイト対策」を看板に出すかは、元データをどうするかと一緒に決める必要がある。G0 は「今ある元データの中で、より役に立つ 3 万件を選ぶ」直しで、元データの不足は直せない。
